# Research — Versioning & Compatibility

**Date:** 2026-10-13. **Status:** technical design research, not implemented policy. **Authority:** [spec.md](spec.md), constitution, current repository contracts. Decisions below resolve technical choices without changing requirements.

## Repository evidence inventory

- `model/product-model.json` currently owns `model_version: "1.0.0"`; canonical lifecycle/phase/gate/decision relationships are consumed by validators and schemas.
- `SKILL-CONTRACT.md` explicitly says no distributable skills are published; `registry/skills.json` has `registry_version: 1` and an empty `skills` array. `manifest.yaml` currently rejects unknown fields and does not define a `version` field. Tooling in `.agents/` is not distributable.
- No executable `workflow.yaml` is published; former workflow directories contain README-only references. `schemas/workflow.schema.json` already defines `version` as a string for a future workflow.
- `schemas/project-state.schema.json` requires project/cycle/phase/status/updated_at, allows additional top-level properties, but has no explicit persisted contract-version marker. Durable evidence/decision semantics also live in their own schemas/templates.
- `skills-lock.json.version: 1` is a lock representation marker; `registry/skills.json.registry_version: 1` is a registry format marker, not SemVer proof.
- Existing CI uses Python 3.12; `requirements-registry.txt` pins PyYAML 6.0.2 and existing scripts perform repository and registry validation. No new service, database or release mechanism is needed.
- Spec Modeling Gate is fresh, and `.specify/extensions.yml` is absent. Companion `*-template-guardrails` is absent. Local runtime-verification skill is absent; upstream canonical v1.12.0 was inspected as a design reference, not invoked locally.

## R1 — Component-specific version owners

**Decision:** Product Model uses `model_version`; future skill version belongs in canonical `manifest.yaml.version` alongside canonical SKILL.md behavior; future workflow `workflow.yaml.version`; machine schema contract version is recorded by its stable `$id` in the declared support ledger until a source-owned marker is introduced through explicit schema migration; persisted project-state format uses `contract_version` when migrated. Each version is independent.

**Why:** Avoid repository-wide bump confusion (FR-001–006, US1/US6).

**Alternatives:** Single repo SemVer (rejected: conflates consumers); derive behavioral version from registry hash (rejected: registry is projection); blanket version-field insertion now (rejected: breaks strict manifests/legacy state without rollout).

## R2 — Support baseline and absent release policy

**Decision:** Ledger records explicit supported versions with immutable source ref/hash, scope and statuses. An observed `1.0.0` identifier does not make an artifact published. Empty skills/workflow publication is valid; no autogenerated baselines from HEAD/registry.

**Why:** Compatibility only meaningful relative to a supported reader/data state (FR-007, FR-029).

**Alternatives:** Compare HEAD to nearest prior commit and call it supported (rejected); infer publishing from version number (rejected).

## R3 — SemVer and pre-1.0

**Decision:** Stable (>=1.0.0): breaking → MAJOR; compatible new behavior → MINOR; behavior-preserving correction → PATCH. Multiple impacts choose highest required bump. An initial/unpublished version is assignment, **not** backward compatibility proof. For 0.y.z: incompatible change requires at least MINOR boundary and explicit support/migration notice; compatible addition may use MINOR; fixes PATCH. Never silently repurpose an existing 0.y.z contract. Identical version + changed public behavior fails release readiness, even if code diff is small.

**Why:** Operationally deterministic while preserving explicit pre-1.0 risk (FR-004–005).

**Alternatives:** Treat all 0.x changes as safe (rejected); require MAJOR for pre-1.0 (impossible without stable transition semantics).

## R4 — Structural vs semantic proof

**Decision:** Deterministic checker understands field requiredness, removed outputs, enum growth under strict readers, ID/path/reference breakage, version/range constraints and syntax. Unknown reader tolerance and behavioral equivalence return `review_required` or `unassessed`, never automatic `compatible`. Human review must identify affected authority and concrete evidence; final verdict distinguishes evidence type.

**Why:** Additive enum/field changes may break strict consumers (FR-008–014, FR-024–029).

**Alternatives:** JSON diff only (misses semantics); always assume breaking (hides true unassessed scope); execute skills in validator (out of scope and not deterministic).

## R5 — Offline assessor and CI

**Decision:** CLI `scripts/check_compatibility.py` reads pinned baseline + candidate artifacts and declared dependents; emits deterministic machine-readable assessment and human summary without mutating files. A non-green status blocks required CI, with separate diagnostic classes for confirmed breakage versus missing review/coverage. No network or hidden runtime startup.

**Why:** Integrates with current Python 3.12 CI and local Windows workflow (US4, FR-024–028).

**Alternatives:** Hosted service (over-scoped); green-by-default unknown (unsafe); write registry/manifest during check (violates read-only boundary).

## R6 — Data migration protocol

**Decision:** Opt-in, explicit source/target version plan; read/validate originals; dry-run result; backup or copy-on-write with atomic replacement where supported; per-record receipts and stable migration IDs; reruns no-op or verify; partial failure recorded with recovery path. Evidence provenance, assumptions, decisions and history are invariant. An irreversible exceptional transform needs explicit approval and residual-risk record.

**Why:** Durable project data outlives repo edits (FR-017–020, US3).

**Alternatives:** Silent in-place repair during validation (unsafe); always rewrite old files (breaks history and trust).

## R7 — Deprecation lifecycle

**Decision:** Explicit active/deprecated/unsupported/removed transitions with effective version boundary, replacement or none, support window, consumer list, migration obligations and removal preconditions. Emergency exception retains the fact that the change is breaking. No release automation.

**Why:** Deprecation notice is not equivalent to removing a skill (FR-021–023, US5).

**Alternatives:** Delete immediately when flagged deprecated (unsafe); never allow emergency exceptions (inflexible).

## R8 — Strict reader rollout

**Decision:** First make reader/contracts capable of handling new version metadata and legacy absence by explicit detection; then update templates/fixtures/writers; only tighten validator to require metadata for **newly distributable** artifacts after compatibility baseline is documented. No retrospective claim that empty registry means external consumers are compatible.

**Why:** `SKILL-CONTRACT.md` currently rejects unknown manifest fields; readers must be updated before writers (FR-012, FR-031).

**Alternatives:** Add `version` to manifest immediately and expect old strict reader to tolerate it (known break); duplicate version into SKILL.md and registry as competing authority (drift).

## R9 — CI and proof freshness

**Decision:** Assessment stores compared source commits/digests and checker/policy revision. Static checks are not skill behavioral tests, migration tests are not proof of user migrations, and CI green is not a published release. Invalidate affected claims when inputs change.

**Why:** Conforms to constitution and canonical runtime catalog `VERIFY-003` (FR-027).

**Alternatives:** Persist `passed: true` without revision binding (stale success).
